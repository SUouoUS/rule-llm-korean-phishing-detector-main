## 1. 배경 — 왜 Rule을 고치게 됐나

정상 택배 배송 알림 2,409건(class 3, 본 분할에서 제외한 별도 평가셋)을 Rule에 넣었더니 **899건(37.3%)을 스미싱으로 오판**했다. 전부 정상 문자다. LLM은 같은 데이터에서 오탐 0건이었다.

원인을 전체 데이터에서 분해한 결과 **딱 두 가지**였고, 서로 겹치지 않았다.

| 원인 | 건수 | 걸린 신호 | 실제 내용 |
|---|---|---|---|
| 쿠팡 **공식** 링크 | 599 | `url` (가중치 2) | `https://coupang.com/photoN` |
| 한진 "접수**제한**" | 300 | `urgency` (가중치 1) | "부피초과 상품은 접수제한되오니…" |

> 💡 임계값이 1이라 `urgency` 하나(1점)만으로도 양성이 된다. 그래서 "제한" 한 단어가 300건을 만들었다.

## 2. 만든 수정 — 옵션 2개

`rule_engine/detector.py`에 플래그로 추가했다. 끄면 기존 Rule과 완전히 동일해서 **개선 전 결과를 언제든 재현**할 수 있다.

### `USE_DOMAIN_ALLOWLIST`
택배사 공식 도메인(및 하위 도메인)은 URL 신호에서 제외.

```python
OFFICIAL_DOMAINS = [
    "coupang.com", "cjlogistics.com", "hanjin.com", "hanjin.co.kr",
    "epost.go.kr", "lotteglogis.com", "ilogen.com", "kdexp.com",
]
```

- **출처 확인 완료**: 8개 전부 루트 HTTPS 접속 + 페이지 title 확인 (근거는 `detector.py` 주석에 날짜와 함께 기록)
- `hanjin.co.kr` → `www.hanjin.com` 리다이렉트되는 공식 별칭이라 유지
- **SLX(`slx.co.kr`)는 제외했다.** 데이터에 300건 있지만 오탐이 0이고, "데이터를 보고 목록을 늘리지 않는다"는 원칙 때문. ← 논문에 쓸 방법론적 선택

### `USE_URGENCY_CONTEXT`
`접수\s?제한` 안의 "제한"만 긴급성 신호에서 제외.

## 4. Rule 임계값 전수 조사 → 천장 0.83

> 🚨 **이 절의 결론은 10/29에 뒤집혔다.** 당시 기록으로만 볼 것.

Validation에서 임계값을 0~4까지 전부 돌렸다.

|---|---|---|---|---|
| 0 | 1.0000 | 1.0000 | 0.6378 | 전부 양성, 무의미 |

**당시 해석**: 임계값 1이 이미 가장 느슨한 설정이고, Rule이 놓친 191건은 점수가 정확히 0(신호 0개)이므로 임계값으로는 도달 불가 → "천장 0.83은 구조적"

## 7. Test 재평가가 불필요해졌다 (5시간 30분 절약)

### 문제
Test 2,383건은 1회만 쓰기로 했는데 이미 썼다. Rule을 수정했으니 원칙상 재평가해야 하고, 재평가하면 LLM을 다시 돌려야 한다 — **1차 때 5시간 30분** 걸렸다.

### 해결
Rule 점수는 **문자 내용만** 보고 계산된다. 정답(라벨)은 안 본다.
→ **라벨을 읽지 않고** "Rule 점수가 바뀌었나?"만 확인할 수 있다. 안 바뀌었으면 Hybrid 예측도 안 바뀌므로 재평가가 필요 없다.

`evaluation/check_test_rule_invariance.py` (`usecols`로 `content`만 읽어 라벨을 메모리에 올리지 않음)

```
Test 2,383건 (라벨 미사용)
공식 도메인 URL 포함: 0건
"접수제한" 포함: 0건
Rule 예측(>=1)이 바뀐 메시지: 0건
→ Test 재평가 불필요
```

> ✅ **기존 Test 결과가 그대로 최종이다.** Rule F1 0.888 / LLM 0.730 / Hybrid 0.922, McNemar p < 0.001.
> 성능을 측정하지 않았으므로(라벨 미사용) Test 1회 사용 원칙을 깨지 않았다.

## 9. 같이 발견한 기존 Rule 한계 (안 고쳤음)

`URL_PATTERN`의 "스킴 없는 도메인" 분기가 `com|net|org|kr|co.kr`만 받는다.

```
https://bit.ly/abc  → 탐지 O
bit.ly/abc          → 탐지 X
vo.la/abc           → 탐지 X
abc.xyz/a           → 탐지 X
```

단축 링크는 실제 스미싱의 주요 수단이라 무게 있는 구멍이다. 고치면 base 결과가 바뀌어 전체 재평가가 필요하므로 손대지 않았다.

> 📌 **10/29 후속**: 오류 분석에서 이 구멍이 실제 미탐의 원인으로 확인됐다(희귀 TLD 7건 + `bit.ly` 2건). 예상보다 중요한 발견이었다.
